# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git conventions

- Never add `Co-Authored-By` trailers or "Generated with Claude Code" lines to commit messages or PR descriptions.
- Work on a feature branch; `develop` is the main branch.

## Commands

```bash
yarn install                 # deps (Node via nvm, corepack-enabled yarn)
yarn start                   # recreate backend containers + reset dev data + vite dev server
yarn serve                   # vite dev server only (backend containers must already be running)
yarn compose:new             # recreate backend containers (docker compose) and reload presets
yarn build                   # production build to dist/
yarn lint                    # vue-tsc --noEmit && eslint && prettier --check  (also runs as git pre-push hook)
yarn lint:fix                # eslint --fix + prettier --write
yarn lint:tsc                # type-check only
yarn test                    # vitest in watch mode
yarn test:ci                 # vitest --run --coverage
yarn vitest run src/utils/__tests__/quantity.test.ts   # single test file
yarn vitest run -t "pattern"                           # tests matching a name
yarn components              # regenerate src/auto-import.d.ts (global component typings)
yarn firmware [release]      # pull firmware.ini for a firmware release and check out the brewblox-proto submodule at its proto_sha
yarn redis / yarn spark      # reset datastore widgets / Spark blocks from dev/presets
yarn redis:save / yarn spark:save   # overwrite dev/presets with the current backend state
```

The dev UI is served at <https://localhost:8080/ui>; the API is proxied to traefik on `:9001` (`vite.config.mts`, `dev/utils.mjs`). Dev scripts talk to the unauthenticated admin entrypoint on `:9601`. The self-signed CA lives in `dev/traefik/minica.pem`.

Tests live in `__tests__/` directories next to the code they test (`src/utils/__tests__`, `src/plugins/*/__tests__`). `test/setup.ts` installs Quasar and Pinia for every test.

Lint conventions enforced by config: prettier with sorted imports (builtin → third-party → `@/` → relative), single quotes, `max-len` 100, single attribute per line in templates, multi-word component names (except `Card`, `Toolbar`), explicit function return types (warn).

## Architecture

Vue 3 + Quasar + TypeScript + Pinia, built with Vite. Block/service types come from the `brewblox-proto` git submodule (generated from the firmware `.proto` files), linked into `node_modules` as a `portal:` dependency, so a checkout of the submodule is live without reinstalling; `yarn firmware` checks out the commit matching a firmware release and `firmware.ini` records that release. Clone with `--recurse-submodules` or run `git submodule update --init`.

### Plugins and features

`src/plugins/*` are Vue plugins (`install(app)`) registered in `src/main.ts`. They do not talk to each other directly; they register **features** in `useFeatureStore()` (`src/store/features`):

- `WidgetFeature` — renders a `Widget` (persisted JSON blob) on a dashboard. `feature.id` matches `widget.feature`.
- `ServiceFeature` — gives a `Service` its own page (`pageComponent`) and config component, plus `onStart`/`onRemove` hooks.
- `WatcherFeature` — always-mounted headless components (e.g. `SparkWatcher`).

Feature `component`/`wrapperComponent`/`editor` fields are **string names of globally registered components**, not component objects. Register with `cref(app, Component)` (returns the name) or `globRegister(app, import.meta.glob(...))`. Everything under `src/components/**` and each plugin's `components/**` is glob-registered, so those components are used in templates without imports; `src/auto-import.d.ts` (generated by `yarn components`) provides their types — regenerate it after adding or renaming a global component.

### Persistent state and events

- Pinia stores in `src/store/*` hold dashboards, widgets, services, etc. Persistent objects are kept in two-way sync with the Redis datastore through `src/database` (full load at startup, then change events). Objects that need post-load initialization are added to `startup` in `main.ts`.
- `src/eventbus.ts` is the MQTT client. Plugins `subscribe()` to topics and `addListener()` for callbacks; the Spark plugin receives block state and patch events this way.

### Spark plugin (`src/plugins/spark`)

One directory per block type under `features/`, each an `index.ts` plugin that registers:

- a `BlockSpec` (`generate()` default data, `analyze()` → status string, `hasRelations`) in `useBlockSpecStore()`,
- `BlockFieldSpec[]` describing editable/graphable fields (`component` is the name of a `*ValEdit` component; `graphed: true` fields feed history graphs as `service/block/field[unit]`),
- a `WidgetFeature` spread from `genericBlockFeature` (`generic.ts`), which sets `wrapperComponent: 'BlockWidgetWrapper'`.

`BlockWidgetWrapper.vue` resolves the widget's `{serviceId, blockId}` config to a block from `useSparkStore()` and `provide()`s it under `BlockKey`; widget components `inject(BlockKey)` (or use the `useBlockWidget` composable for `patchBlock`, `graphConfig`, etc.) and can assume the block is present. `DeprecatedObject`, `InactiveObject`, and `UnknownBlockWidget` cover blocks without a real feature.

The block list of a service and its relations diagram (`service/SparkPage.vue`, `service/SparkListView.vue`) only show blocks whose type has a registered `BlockSpec`.

### Other plugins

- `history` — graphs/metrics/session logs backed by the history service (Victoria Metrics).
- `builder` — the process-view editor; parts live in `builder/parts`, blueprints (transitions per part type) in `builder/blueprints`. Flows are calculated in `flowNetwork.ts` by solving the layout as a linear network (nodal analysis: friction is resistance, pumps and inlets are pressure sources). `use-flow-parts.ts` recalculates whenever the computed transitions change, so blueprints may read Spark block state directly without extra watchers.
- `quickstart` — multi-step wizards that generate services, dashboards, widgets and blocks; see `src/plugins/quickstart/README.md` for the task/`config`/`actions` protocol.
- `wizardry` — the generic widget/block creation wizard dialogs.

### Dev backend

`docker-compose.yml` runs the backend stack (traefik, eventbus/mosquitto, redis, victoria, history, auth, two Spark simulators `sparkey` and `spock`, usb-proxy, node-red). Traefik config is in `dev/traefik/`. `yarn start` resets backend data to `dev/presets/` on every run; commit updated presets after `yarn redis:save`/`yarn spark:save` to make changes permanent.
